# oidc-caep-risc-rust

A confidential OpenID Connect relying party for a traditional Rust application, and a CAEP and RISC receiver on one Shared Signals poll stream. Authorization Code with PKCE (S256) is required. Client authentication is `client_secret_basic`, `client_secret_post`, or `private_key_jwt`. A public client (`none`) is refused.

`signals` defaults to on. `signals: false` turns CAEP and RISC off: the receiver does not start, transmitter metadata is not required, and the authorization request does not include `ssf.read` or `ssf.manage`. `DEFAULT_SCOPES` still names those two scopes. They are removed after that default is applied. The shipped demo omits `signals`, so they stay on.

The license is the MIT License in `LICENSE`. A pull request merged into `main` publishes the crate to crates.io after the test workflow succeeds on that commit. A direct push does not. The token is the `CARGO_REGISTRY_TOKEN` repository secret. A release happens when the library's files changed since the last release's tag: `publish.yml` takes one patch above the highest published version, publishes it, and creates the matching tag and GitHub Release. A change to tests, the demo, or the docs releases nothing. `src/suite.rs` is the test harness (it is not named `*_test.rs`), and `publish.yml` excludes it with the other tests. To choose a version or start a new minor, raise `VERSION`; the version is stamped in CI and is not committed, so the manifests can trail what is published. `develop` and `main` are the branches the test workflow runs.

Rust edition 2021. RSA (PKCS #1 v1.5 and PSS) uses the `rsa` crate, ECDSA `p256`, `p384` and `p521`, EdDSA `ed25519-dalek`. Every algorithm in `keys::ASYMMETRIC` verifies, and `src/profile_test.rs` signs an ID token and a SET in each of them; do not list an algorithm there that `verify_signature` cannot check. ID tokens default to `["RS256"]` (`idTokenSigningAlgs`).

Issue #18 (shared with the six sibling libraries, same keys and defaults): `dpop` (`auto`/`always`/`never`, ES256 only, key generated at creation or `dpopKey`), `src/dpop.rs`; `acrValues` and the `acr` check; `require_pushed_authorization_requests`; `idTokenSigningAlgs` intersected with the advertised list; `requireIdTokenTypAndAtHash`; `config::apply_defaults`, which `RelyingParty::create` runs too, so a directly created client gets the same defaults and redirect-URI rule as `from_file` (`allowInsecure` no longer relaxes redirect URIs); and the session cache (`complete_session`, `session_access_token`, `remove_session`, `SessionStore`). `SignalsReceiver` takes `relying_party` to authorize transmitter calls (DPoP-aware) and to clear ended sessions from that cache. The tests are `src/profile_test.rs`, with their own configurable stub provider; the suite's stub transmitter accepts `DPoP app-token` with a verified proof and can demand a nonce.

The reverse-proxy gaps (iya-sts's remote PEP, rcbj/iya-sts#1760), 0.3.0: `MemorySessionStore` is bounded (`sessionMaxEntries` 10000, `sessionTtlSec` 86400, both through `apply_defaults`; oldest-written evicted, expired never answered; `stats()`); `SignalsReceiver::health()` (`ReceiverHealth`), `ReceiverOptions::on_error`, a `stop()` woken by a condvar, and one poll thread with no thread spawned per poll; the `tokio` feature (`src/async_api.rs`), `spawn_blocking` around the same blocking calls, not a second HTTP stack. No TLS-verification skip was added: `tlsCa` with the listener's chain is the answer to a CA regenerated on every start. The tests are `src/proxy_gaps_test.rs`. 0.3.0 rather than 0.2.2 because the default store now evicts, which a 0.2 caller did not agree to. Whether the six siblings get the same bounded store and receiver health is issue #18's business; only this library changed.

The embedded PEP (#46, iya-sts#1206 work item 7), behind the `pep` feature (`local` adds the engine): `src/pep.rs` wires in the shared `iya-pep` crate (rcbj/iya-pep-rust).
- `RelyingParty::create` builds and starts it from the `pep` section:
  - `pdpUrl` defaults to the issuer and `application` to `clientId`;
  - `signals` and `tlsCa` are the library's;
  - it refuses an assertion key that is the `private_key_jwt` or DPoP key (by JWK thumbprint).
- Without the feature, a `pep` section is refused rather than ignored.
- `decide` / `decide_session` adapt a `Login` (`preferred_username`, else `sub`; the ID token claims) into the PEP's subject.
- `SignalsReceiver::new` adds `pep-policies-changed` to `events_requested` and registers the hand-over when the relying party's PEP wants events (`local`, or `central` with a Permit cache).
- `src/pep_test.rs` has its own stub PDP, and reuses `profile_test.rs`'s provider for the receiver test.
- **The dependency is a git dependency on iya-pep-rust's `feature/1`** until that crate's first release. Switch it to the crates.io version then, because crates.io refuses a git dependency at publish.
- The live test is `scripts/live_iya_sts.py --pep` (see *Tests*). It found two defects the stubs had not: `resolve_config` (so `from_file` and the demo) dropped the `pep` section, and a receiver reusing a poll stream made before the PEP wanted events never got `pep-policies-changed`. `ensure_stream` now PATCHes the missing event types into a reused stream (a refusal goes to `on_error` and the PEP's heartbeat says `excluded`); `src/pep_test.rs` holds both.
- **The lock pins iya-pep `c0d61ca`** (feature/1): central hands `context.advice`, and local writes the caller fact as the DN the registration names.
- **The AuthZEN tests** (the owner: tests for the remote PEP live in each client library's repo; original, not copied from iya-sts or iya-pep; central and local must ALWAYS give the same answer). `src/tests/authzen_cases.json` is the table (`src/**/tests/**`, so it releases nothing): catalogue rows, ALFA policies with `references` the live run adds through the editor (`add-policy-reference`; this ALFA dialect has none) and `xacml` (iya-sts's stored document, lines, which the offline stub serves; regenerate with `AUTHZEN_XACML_OUT`), users for the PIP, and the cases. `src/authzen_test.rs` (feature `local`) runs it offline against its own stub PDP and live as the ignored `live_central_equals_local`, driven by `scripts/live_authzen.py` (`live_iya_sts.py --authzen`, container `iya-sts-live-oidc-caep-risc-rust-authzen`, port 18526, target volume `oidc-caep-risc-rust-authzen-target`). Never weaken a case to make the live run pass: `knownLocalDefect` only keeps the offline run (CI) green while a local defect is open, and must still be wrong there. The live run against #2026–#2028 failed 5 of 54 on the FGA application `authzen-ledger` until both were fixed: iya-sts's `FgaPep.decideAccess()` now resolves a reference against the set the scoped pull's closure comes from (rcbj/iya-sts feature/2027, 2983a43d0), and iya-pep 3f145ef adds `urn:sts:xacml:fga:application`/`fga:stage` for an application in the catalogue's `fgaApplications` (which the offline stub now serves). With both, the live run is 54 of 54 central == local == expected (2026-11-24).
- **The user guide is `docs/remote-pep.md`**, generated for the four Rust libraries from one outline; keep its sections in step with the siblings' when changing it. The README's section is a summary that links to it.

## Layout

| Path | What it is |
|---|---|
| crate `oidc-caep-risc` | The library. `from_file`, `authorize`, `complete`. |
| `src/suite.rs` | `cargo test`. A stub provider and a stub transmitter. No live iya-sts. |

| `src/pep_test.rs` | #46: the `pep` section and its defaults, the three-key refusal, the `Login` adapter, `decide`/`decide_session` against a stub PDP, the event through `SignalsReceiver`, `local` failing closed and then deciding in process. |

## Usage

```rust
let rp = oidc_caep_risc::RelyingParty::from_file("oidc.json")?;
let request = rp.authorize()?;
let who = rp.complete_session(&query, &request, &session_id)?;
let access = rp.session_access_token(&session_id)?;
```

Keep the transaction (state, nonce, code verifier, acr_values) until the browser returns. Tokens stay in this process.

## Tests

```bash
docker build --target test .
```

The `test` stage runs `cargo test --all-features` and `cargo build --lib` in `rust:1-bookworm`. GitHub Actions uses that command. Do not run Cargo on the host. The demo image does not run the suite. `start_transmitter` calls `ssf_keys()` before it accepts a connection. Those two RSA-2048 keys used to be generated inside the first `/jwks`, which can outlast the library's 15 s HTTP timeout on a busy runner (#41). `start_op` already calls `alg_keys()` for the same reason.

The stub tests do not start iya-sts. `python3 scripts/live_iya_sts.py` does, unless `IYA_STS_URL` names one that is already running. Its order is the user's: it copies the checkout (no `demo/generated`, `.git`, `target`) to a scratch context, rewrites only that copy's URLs (never `tlsCa`), runs the install script (which writes the client secret and the chain), THEN builds the demo image, checks the image's `demo/generated` holds only `idp-ca.pem` and that it equals the saved file (`tlsCaInImage` in the result), and THEN runs the demo with only `client-secret` mounted and `TLS_CA_REFRESH=0`. Secrets reach docker as `-e NAME`, and no log line carries a sign-in URL (each request is logged by a fixed label). No script prints a password or secret, or a path or plan derived from one (the dry run shows `<client secret>`): the client secret and a generated test-user password (`demo/generated/<user>.password`) are files created 0600, and only the password file's path is printed. Every `ssl` context in `scripts/` sets TLS 1.2 as the minimum. It signs the demo in and checks two Shared Signals events on `GET /live-status`. `--pep` (or `LIVE_PEP=1`) adds the embedded PEP (#46) and needs an iya-sts with #2026–#2028 (the nightly does not pass it until they reach `main`; point `IYA_STS_IMAGE` at an image built from them). After the install script it provisions the PEP through `/admin-api` as `docs/remote-pep.md` says: the service account `pep-oidc-demo` in `remote-peps`, a P-256 key made with the host's `openssl` in `demo/generated/pep-key.pem` (0600, never printed, kept out of the image by `.dockerignore`), `issue-pep-credential` with its CSR and the demo's application, the catalogue row `subject.acr` → `urn:example:acr`, and a realm root (the demo enforces no fine-grained authorization) that permits `read` on an `order` when `acr` arrived and denies everything else. The demo runs with a `central` `pep` section, mounting only the client secret and the PEP's key: `GET /orders/42` must be 200 and `POST /orders/42` 403. Then again with `OIDC_CONFIG` naming the image's `demo/oidc.pep-local.json` (`local`): the same two, then the root moves to a policy that denies `read`, and within `PEP_FLIP_TIMEOUT` seconds (30) the GET must be 403 with `pep-policies-changed` received (the fallback poll stays at its 300 s default, so `via` is `event`). The result's `pep` object holds each check, and `/live-status` carries the PEP's `status()` under `pep`. `LIVE_KEEP=1` leaves both containers running after the run for a post-mortem. The nightly workflow runs both. `.github/workflows/nightly.yml` runs at 07:02 UTC (`2 7 * * *`) and on `workflow_dispatch`. `IYA_STS_IMAGE` starts a fresh container from an image already built; without it or `IYA_STS_URL` the script clones and builds iya-sts `main`. `LIVE_STS_PORT` defaults to 18516 and `LIVE_DEMO_PORT` to 18616; the script refuses 3000, 8081, and 18481 through 18495. Registration runs `scripts/configure_iya_sts.py` with the host's stdlib python3, never Cargo. Always use a fresh iya-sts: a second registration of the same client fails. `--authzen` (or `LIVE_AUTHZEN=1`) is a different run with no demo or sign-in: `scripts/live_authzen.py` provisions a fresh iya-sts for `src/tests/authzen_cases.json` (two applications, a `central` and a `local` PEP each with its own key) and runs the ignored `authzen_test::live_central_equals_local` in `rust:1-bookworm` on the host network; it exits non-zero on any mismatch and prints `cases`, `centralEqualsLocal`, `asExpected` and `mismatches` last. The nightly does not run it (main lacks #2026–#2028).

## Demo

`docker-compose.yml` sets `network_mode: host`. The process binds `PORT`, default 3000. `ENV PORT=3000` in the image keeps an unset value on 3000, and the health check calls `http://127.0.0.1:${PORT}/healthz`.

```sh
docker compose up --build
```

`GET /healthz` returns `ok`. `GET /` is the page. `GET /login` redirects to the provider. `GET /callback` completes the sign-in. `POST /logout` ends the local session. `GET /live-status` reports the sign-in and the Shared Signals events this process has accepted, and (with a `pep` section) the PEP's `status()` under `pep`; its `syncToken` is the version of the policy held, not a credential. It does not include tokens. `GET /orders/<id>` is read and any other method write, decided by the PEP: 401 without a sign-in, 200, 403, or 503 on `Unavailable`. The signed-in page has two tabs: **Session** (`/`) and **Policy enforcement** (`/?tab=pep`), the embedded PEP's numbers, drawn by `pep_fragment()` from the PEP's `Status` and refreshed every 2 s by `demo/public/pep.js` from `GET /pep-status.html`; `GET /pep-status` is the same as JSON (milliseconds for every time). Both need a sign-in, and carry nothing secret. Only this library's demo has the tab so far: rcbj wants the details settled here before the SAML, WS-Federation and GNAP demos get one.

A loopback redirect follows `PORT` in the running server and in `scripts/configure_iya_sts.py`. Any other host is left as written. An explicit `--public-url` or a non-empty `PUBLIC_URL` replaces the origin and keeps the path. The running container's `PORT` wins over the shell's when the script registers the application. `pollIntervalMs` is a millisecond pause, not a port.

Open `http://127.0.0.1:$PORT` after the provider is up. Do not bind port 3000 or 8081 while another demo or iya-sts is already using them.

## Trust chain (`tlsCa`)

`tlsCa` (default `generated/idp-ca.pem`, relative to `demo/`) is iya-sts's TLS listener CA trust chain. `scripts/configure_iya_sts.py` writes it on every run through `scripts/trust_chain.py`'s `save_trust_chain()`: the whole chain from `GET /tls/server-certificate` (leaf, TLS Issuing CA, Intermediate, Root), falling back to the handshake's chain, and prints the path, the anchor's subject and SHA-256. `src/http.rs` already split the file and added every PEM block as a native-tls root (`native_tls::Certificate::from_pem` alone reads only the first), native-tls verifies the host name, and nothing pins, so the library needed no change; `src/trust_chain_test.rs` holds all of that. The demo image carries the chain from build time: `.dockerignore` is `demo/generated/*` then `!demo/generated/idp-ca.pem`, the build stage copies only `demo/main.rs` and `demo/public` (so a new chain does not rebuild the binary), and the final stage's `COPY demo demo` lands it at `/app/demo/generated/idp-ca.pem`. With no chain file the same COPY carries nothing from `demo/generated` and the build succeeds. Rebuild the image after re-running the install script against a different iya-sts. `demo/entrypoint.sh` still refreshes the chain at start unless `TLS_CA_REFRESH=0`. The `HEALTHCHECK` reads `$PORT` (it read `$$PORT`, the shell's PID, until #8).
