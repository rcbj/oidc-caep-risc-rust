# oidc-caep-risc-rust

A confidential OpenID Connect relying party for a traditional Rust application, and a CAEP and RISC receiver on one Shared Signals poll stream. Authorization Code with PKCE (S256) is required. Client authentication is `client_secret_basic`, `client_secret_post`, or `private_key_jwt`. A public client (`none`) is refused.

`signals` defaults to on. `signals: false` turns CAEP and RISC off: the receiver does not start, transmitter metadata is not required, and the authorization request does not include `ssf.read` or `ssf.manage`. `DEFAULT_SCOPES` still names those two scopes. They are removed after that default is applied. The shipped demo omits `signals`, so they stay on.

The license is the MIT License in `LICENSE`. A pull request merged into `main` publishes the crate to crates.io after the test workflow succeeds on that commit. A direct push does not. The token is the `CARGO_REGISTRY_TOKEN` repository secret. A release happens when the library's files changed since the last release's tag: `publish.yml` takes one patch above the highest published version, publishes it, and creates the matching tag and GitHub Release. A change to tests, the demo, or the docs releases nothing. `src/suite.rs` is the test harness (it is not named `*_test.rs`), and `publish.yml` excludes it with the other tests. To choose a version or start a new minor, raise `VERSION`; the version is stamped in CI and is not committed, so the manifests can trail what is published. `develop` and `main` are the branches the test workflow runs.

Rust edition 2021. RSA (PKCS #1 v1.5 and PSS) uses the `rsa` crate, ECDSA `p256`, `p384` and `p521`, EdDSA `ed25519-dalek`. Every algorithm in `keys::ASYMMETRIC` verifies, and `src/profile_test.rs` signs an ID token and a SET in each of them; do not list an algorithm there that `verify_signature` cannot check. ID tokens default to `["RS256"]` (`idTokenSigningAlgs`).

Issue #18 (shared with the six sibling libraries, same keys and defaults): `dpop` (`auto`/`always`/`never`, ES256 only, key generated at creation or `dpopKey`), `src/dpop.rs`; `acrValues` and the `acr` check; `require_pushed_authorization_requests`; `idTokenSigningAlgs` intersected with the advertised list; `requireIdTokenTypAndAtHash`; `config::apply_defaults`, which `RelyingParty::create` runs too, so a directly created client gets the same defaults and redirect-URI rule as `from_file` (`allowInsecure` no longer relaxes redirect URIs); and the session cache (`complete_session`, `session_access_token`, `remove_session`, `SessionStore`). `SignalsReceiver` takes `relying_party` to authorize transmitter calls (DPoP-aware) and to clear ended sessions from that cache. The tests are `src/profile_test.rs`, with their own configurable stub provider; the suite's stub transmitter accepts `DPoP app-token` with a verified proof and can demand a nonce.

The reverse-proxy gaps (iya-sts's remote PEP, rcbj/iya-sts#1760), 0.3.0: `MemorySessionStore` is bounded (`sessionMaxEntries` 10000, `sessionTtlSec` 86400, both through `apply_defaults`; oldest-written evicted, expired never answered; `stats()`); `SignalsReceiver::health()` (`ReceiverHealth`), `ReceiverOptions::on_error`, a `stop()` woken by a condvar, and one poll thread with no thread spawned per poll; the `tokio` feature (`src/async_api.rs`), `spawn_blocking` around the same blocking calls, not a second HTTP stack. No TLS-verification skip was added: `tlsCa` with the listener's chain is the answer to a CA regenerated on every start. The tests are `src/proxy_gaps_test.rs`. 0.3.0 rather than 0.2.2 because the default store now evicts, which a 0.2 caller did not agree to. Whether the six siblings get the same bounded store and receiver health is issue #18's business; only this library changed.

Add Subject / Remove Subject (the owner: by default a subscribing app receives CAEP and RISC events only about users with an active session on it; iya-sts#2234; the same as wsfed-caep-rust f41f08d and gnap-caep-risc-rust #44): `SignalsReceiver::track` calls `add_subject_endpoint` (SSF 1.0 §8.1.3.2; `iss_sub` with the transmitter's issuer and `person`, else `email`; `verified: true`) once per person, and `untrack` or an event-ended session calls `remove_subject_endpoint` (§8.1.3.3) when that person's last tracked sign-in is gone and only for a subject the transmitter accepted (the `added` set). Calls go through `transmitter_call` (the `relying_party` token, DPoP-aware), inline (caller's thread; the poll thread for an event-ended session), no new timer, never retried; a refusal or failure goes to `on_error` and `ReceiverHealth`'s `subjects_added`/`subjects_removed`/`subject_refusals`/`subject_failures`/`last_subject_error`, never failing a sign-in. Skipped while not running (signals off), without the endpoints, with `ReceiverOptions::add_subjects` false, or `ssf.addSubjects: false` in the relying party's configuration (validated as a boolean by `resolve_config` and `apply_defaults`). Sessions tracked before `start` are added at `start`. The tests are `src/subjects_test.rs`; the stub transmitter publishes the endpoints on request (`subject_endpoints`), records each call (`subject_calls`) and can refuse (`subject_status`). `start_provider` now makes the provider's RSA key before it answers, as `start_transmitter` and `start_op` already did (the 15 s timeout, #41). The demo tracks every sign-in at `/callback` (not only the first; gnap's demo had that bug).

The embedded PEP (#46, iya-sts#1206 work item 7), behind the `pep` feature (`local` adds the engine): `src/pep.rs` wires in the shared `iya-pep` crate (rcbj/iya-pep-rust).
- `RelyingParty::create` builds and starts it from the `pep` section:
  - `pdpUrl` defaults to the issuer and `application` to `clientId`;
  - `signals` and `tlsCa` are the library's;
  - it refuses an assertion key that is the `private_key_jwt` or DPoP key (by JWK thumbprint).
- Without the feature, a `pep` section is refused rather than ignored.
- `decide` / `decide_session` adapt a `Login` (the `username` claim, else `preferred_username`, else `sub`; the ID token claims) into the PEP's subject.
- `SignalsReceiver::new` adds `pep-policies-changed` to `events_requested` and registers the hand-over when the relying party's PEP wants events (`local`, or `central` with a Permit cache).
- `src/pep_test.rs` has its own stub PDP, and reuses `profile_test.rs`'s provider for the receiver test.
- **The dependency is a git dependency on iya-pep-rust's `feature/1`** until that crate's first release. Switch it to the crates.io version then, because crates.io refuses a git dependency at publish.
- The live test is `scripts/live_iya_sts.py --pep` (see *Tests*). It found two defects the stubs had not: `resolve_config` (so `from_file` and the demo) dropped the `pep` section, and a receiver reusing a poll stream made before the PEP wanted events never got `pep-policies-changed`. `ensure_stream` now PATCHes the missing event types into a reused stream (a refusal goes to `on_error` and the PEP's heartbeat says `excluded`); `src/pep_test.rs` holds both.

The receiver reports that state (`requested`/`excluded` at start and after a good poll, `down` after a failed poll or `stop()`; `report_pep_stream` in `src/ssf.rs`), tested in `src/pep_test.rs`; while it is not `requested` a `local` PEP polls at `pollIntervalMs`, else at `fallbackPollMs`.
- **The AuthZEN tests** (the owner: tests for the remote PEP live in each client library's repo; original, not copied from iya-sts or iya-pep; central and local must ALWAYS give the same answer). `src/tests/authzen_cases.json` is the table (`src/**/tests/**`, so it releases nothing): catalogue rows, ALFA policies with `references` the live run adds through the editor (`add-policy-reference`; this ALFA dialect has none) and `xacml` (iya-sts's stored document, lines, which the offline stub serves; regenerate with `AUTHZEN_XACML_OUT`), users for the PIP, and the cases. `src/authzen_test.rs` (feature `local`) runs it offline against its own stub PDP and live as the ignored `live_central_equals_local`, driven by `scripts/live_authzen.py` (`live_iya_sts.py --authzen`, container `iya-sts-live-oidc-caep-risc-rust-authzen`, port 18526, target volume `oidc-caep-risc-rust-authzen-target`). Never weaken a case to make the live run pass: `knownLocalDefect` only keeps the offline run (CI) green while a local defect is open, and must still be wrong there. ## Usage

```rust
let rp = oidc_caep_risc::RelyingParty::from_file("oidc.json")?;
let request = rp.authorize()?;
let who = rp.complete_session(&query, &request, &session_id)?;
let access = rp.session_access_token(&session_id)?;
```

Keep the transaction (state, nonce, code verifier, acr_values) until the browser returns. Tokens stay in this process.

## Demo

`docker-compose.yml` sets `network_mode: host`. The process binds `PORT`, default 3000. `ENV PORT=3000` in the image keeps an unset value on 3000, and the health check calls `http://127.0.0.1:${PORT}/healthz`.

```sh
docker compose up --build
```

`GET /healthz` returns `ok`. `GET /` is the page. `GET /login` redirects to the provider (`?prompt=login` or `select_account` passes that prompt). `GET /callback` completes the sign-in, and when the ID token names no username (or no email) calls UserInfo once (`fill_from_userinfo`) to fill `preferred_username`, `name` and `email` into the session cache. `POST /logout` ends the local session. `GET /live-status` reports the sign-in and the Shared Signals events this process has accepted, and (with a `pep` section) the PEP's `status()` under `pep`; its `syncToken` is the version of the policy held, not a credential. It does not include tokens. `GET /orders/<id>` is read and any other method write, and `GET /attribute-protected` is `Access::new("read", "attribute-protected", "attr1")`, both decided by the PEP (`rp.decide` on the cookie session's `Login`): 401 without a sign-in, then the decision's `http_status()`, 200 or 403 on a Deny and on any PEP failure (`Unavailable`, a panic included); no relying party is 403 too: an enforcement point that cannot say yes says no. The image carries `demo/oidc.json` from build time, so rebuild after the install script writes the `pep` section.

The signed-in page (`home`) has three tabs: **Session** (`/`; `session_panes`: protections in effect, the ID token's claims, the Token cache with `POST /session/userinfo` and `POST /session/refresh`, the tokens by fingerprint and decoded JWT), **CAEP & RISC events** (`/?tab=events`; `events_panel`: whose events these are, the stream with `POST /signals/verify`, the log; `app.js` polls `GET /api/signals?after=<id>` every 3 s because `GET /events` answers 204) and **Policy enforcement** (`/?tab=pep`; `pep_fragment()` from the PEP's `Status`: Decisions, Cached policy, The PEP, Control plane, and Try it linking `/orders/42` and `/attribute-protected`, refreshed every 2 s by `demo/public/pep.js` from `GET /pep-status.html`, keeping a closed pane closed; `GET /pep-status` is the same as JSON, milliseconds for every time). Both PEP routes need a sign-in (401) and carry nothing secret. Every block is a `<details>` pane (`pane()`), and `demo/public/panes.js` shows a Collapse all / Expand all toggle for the tab shown. `page_for` puts the signed-in top bar together: `site_nav()` (Demo home, and with `pep` Attribute-protected and Order 42) and `user_menu()` (`demo/public/menu.js`: the account, Sign in with another account via `prompt=login`, and Sign out, the only sign-out on the page). The name shown (`display_name`) is the `username` claim, else `preferred_username`, else email, else subject. The SAML, WS-Federation and GNAP demos have the same three tabs, panes and top-bar links.

A loopback redirect follows `PORT` in the running server and in `scripts/configure_iya_sts.py`. Any other host is left as written. An explicit `--public-url` or a non-empty `PUBLIC_URL` replaces the origin and keeps the path. The running container's `PORT` wins over the shell's when the script registers the application. `pollIntervalMs` is a millisecond pause, not a port.

Open `http://127.0.0.1:$PORT` after the provider is up. Do not bind port 3000 or 8081 while another demo or iya-sts is already using them.

## Trust chain (`tlsCa`)

`tlsCa` (default `generated/idp-ca.pem`, relative to `demo/`) is iya-sts's TLS listener CA trust chain. `scripts/configure_iya_sts.py` writes it on every run through `scripts/trust_chain.py`'s `save_trust_chain()`: the whole chain from `GET /tls/server-certificate` (leaf, TLS Issuing CA, Intermediate, Root), falling back to the handshake's chain, and prints the path, the anchor's subject and SHA-256. `src/http.rs` already split the file and added every PEM block as a native-tls root (`native_tls::Certificate::from_pem` alone reads only the first), native-tls verifies the host name, and nothing pins, so the library needed no change; `src/trust_chain_test.rs` holds all of that. The demo image carries the chain from build time: `.dockerignore` is `demo/generated/*` then `!demo/generated/idp-ca.pem`, the build stage copies only `demo/main.rs` and `demo/public` (so a new chain does not rebuild the binary), and the final stage's `COPY demo demo` lands it at `/app/demo/generated/idp-ca.pem`.
